# AI Task System

Закрытая корпоративная система задач для руководителя и узкого круга подчинённых.
Полное ТЗ и дорожная карта — см. артефакт плана (ссылка у владельца проекта).

Текущий статус (актуализировано 17.09.2026 — подробное фактическое описание
архитектуры, голосового пайплайна и текстового AI-чата см. в
`CURRENT_STATE.md`, этот раздел даёт только общую картину): **Этап 1
(Core) + Этап 3 (Meetings, включая автосинхронизацию из Plaud) +
голосовой AI-агент задач/событий (часть Этапов 4–5, реализована раньше
остального Routing Engine) + текстовый AI-чат «Ассистент» в Mini App
(Stage 2, Phases A–F.2, G — персистентная переписка, tool-calling,
streaming, вложения, две стабилизации, генерация файлов)** — сотрудники,
компетенции (единственный профиль соответствия — раздел 6.3 ТЗ
про отдельную зону ответственности сознательно упразднён владельцем
28.08.2026: избыточен рядом с компетенциями и не имел структурного пути к
TaskProfile для будущего AI-подбора; сущность Project тоже упразднена
владельцем 28.08.2026 — привязки к проекту не будет, всё в системе
считается одним контуром), задачи с канбан-доской, права доступа, привязка
Telegram-аккаунтов, встречи (ручная загрузка и автосинхронизация саммари из
Plaud через OAuth, `apps/api/src/plaud/`) с привязкой задач к источнику,
личный календарь руководителя с двусторонней синхронизацией Google Calendar
и участниками встреч (раздел 14.2 ТЗ / концепция «Адъютант», 28.08.2026).
Web App и Telegram Mini App (Этап 2 ТЗ, 31.08.2026) — оба поддерживают
голосовой ввод: диктовка задачи/события через `POST /voice/parse`
(расшифровка Whisper → каскад Claude Haiku/Opus → выполнение действия
сразу на сервере, без отдельного подтверждения на create/update/delete —
см. `CURRENT_STATE.md`), редактирование/удаление существующих задач и
встреч голосом, включая добавление/снятие участников встречи. **Полноценный
входящий Telegram-бот (приём голосовых/текстовых сообщений в чате с ботом)
не реализован** — `TelegramBotService` используется только для исходящих
push-уведомлений, голосовой ввод сейчас работает только через запись в
браузере/WebView Mini App/Web App. AI Meeting Processing (замена Speaker →
имя, разбиение на темы, извлечение задач из протокола) и полноценный AI
Routing Engine (Этапы 4–5 целиком) ещё не начаты — блокируются
офлайн-валидацией точности (Этап 0 ТЗ), для которой пока не собрано
достаточно протоколов встреч и профилей сотрудников.

## Структура репозитория

```
apps/api        NestJS — единое ядро backend (auth, employees, competencies, tasks, meetings, calendar, telegram)
apps/web        Next.js — интерфейс руководителя (десктоп)
apps/miniapp    Next.js — Telegram Mini App (раздел 14.2 ТЗ), свайп-режимы
packages/shared-types  Общие TypeScript-типы api ⇄ web ⇄ miniapp
infra/docker    docker-compose / Dockerfile для продакшена и локального Postgres
```

## Быстрый старт

Требуется Node.js 20+ и PostgreSQL (локально или через Docker). Node проверен на v26.

```bash
npm install

cp .env.example .env
cp .env.example apps/api/.env      # apps/api читает свой .env через @nestjs/config

# поднять Postgres — через Docker...
docker compose -f infra/docker/docker-compose.yml --env-file .env up -d
# ...или через локально установленный PostgreSQL: создать роль/базу
# из POSTGRES_USER/POSTGRES_PASSWORD/POSTGRES_DB в .env вручную.

# применить схему БД
npm run prisma:migrate --workspace=apps/api

# создать руководителя (email/пароль — из SEED_OWNER_EMAIL/SEED_OWNER_PASSWORD
# в apps/api/.env)
npm run seed --workspace=apps/api

# запустить backend (http://localhost:3001) и frontend (http://localhost:3000,
# либо следующий свободный порт, если 3000 занят)
npm run dev:api
npm run dev:web
```

Проверено end-to-end на локальной установке PostgreSQL 17: миграции, сид,
логин, создание сотрудника/задачи, привязка Telegram — всё отработало через
API и в браузере.

## Модель доступа (раздел 5 ТЗ)

- **OWNER** (руководитель) — видит всех сотрудников (полный профиль: email,
  телеграм, статус, компетенции…), все задачи, управляет карточками
  сотрудников и их компетенциями, менять статусы вроде «Возвращена на
  доработку» / «Отменена», единственный может создавать задачи из встречи
  (Plaud).
- **EMPLOYEE** (подчинённый) — видит список коллег (только имена, для выбора
  исполнителя) и задачи, где он исполнитель или постановщик; переводить
  задачу между рабочими статусами (`IN_PROGRESS`, `IN_REVIEW`, `DONE`) может
  только исполнитель (постановщик — не автоматически), комментировать может
  любой, кому задача видна.

Скорректировано владельцем 28.08.2026 (раздел 5/9/10 ТЗ): ставить задачу
друг другу — включая руководителю — может любой участник закрытого круга
через интерфейс (`POST /tasks`), это больше не привилегия только
руководителя. Исключение осталось одно — задача с `sourceMeetingId` (то есть
поставленная по итогам встречи Plaud): её по-прежнему может создать только
`OWNER`, проверка в `TasksService.create`, а не в `@Roles` контроллера,
потому что решение зависит от тела запроса, а не от роли постановщика.
Редактировать задачу (`PATCH /tasks/:id`) может её постановщик или
руководитель; список сотрудников (`GET /employees`) теперь доступен всем —
иначе некому было бы выбрать исполнителя — но подчинённому отдаётся только
`{id, fullName}`, полный профиль по-прежнему только руководителю.

RBAC применяется на уровне API (guard'ы в `apps/api/src/auth` + точечные
проверки внутри сервисов там, где решение зависит от конкретной задачи), а
не только в интерфейсе — раздел 15 ТЗ.

## Календарь и голосовой AI-агент (раздел 14.2 ТЗ / «Адъютант», 28.08.2026)

Владелец описал конечный вид системы: руководитель ставит задачи и события
через единую точку входа — Telegram Mini App, включая голосовые сообщения,
которые AI-агент разбирает на задачу / событие / письмо (подробности —
записка «Адъютант», ссылка у владельца). **Голосовой агент для задач и
событий реализован и работает** в обоих фронтендах (полный поток — см.
`CURRENT_STATE.md`, раздел "Voice pipeline"); не реализованы часть с
письмами (согласовано — всегда через подтверждение, без исключений) и
Plaud MCP-клиент (вместо него сейчас работает OAuth-синхронизация через
Plaud API, `apps/api/src/plaud/`, см. ниже раздел "Встречи и источник
задачи").

- **Риск-иерархия для автономности агента** (согласовано с владельцем):
  задачи — низкий риск, могут дойти до автономности быстрее всех; календарь —
  средний (обратимо, но конфликты); письма — высокий, черновик и подтверждение
  руководителя обязательны **всегда**, не только на старте — раздел 10.3 ТЗ:
  значимые/необратимые действия не переходят в автономный режим по мере
  накопления доверия к остальному.
- **`Event`** (`apps/api/prisma/schema.prisma`) — внутренний календарь,
  источник правды в нашей системе. `status: DRAFT` зарезервирован под черновик
  от будущего голосового агента (raздел 10 ТЗ — ждёт подтверждения, не
  синхронизируется в Google, пока не станет `CONFIRMED`).
- **Двусторонняя синхронизация с Google Calendar** — единственный писатель с
  обеих сторон — руководитель, поэтому конфликты разрешаются last-write-wins
  по времени последнего изменения (`Event.lastModifiedBy` + `updatedAt` vs
  `googleEvent.updated`), без полноценного merge — иначе потребовалась бы
  куда более сложная модель для сценария, которого на практике не будет
  (несколько независимых редакторов одного календаря).
  - `GoogleCalendarConnection` — один на сотрудника (на практике только
    OWNER), refresh-токен хранится зашифрованным AES-256-GCM
    (`SecretBoxService`, `apps/api/src/crypto`) — раздел 15 ТЗ: первый секрет
    в системе, который не просто проверяется, а реально расшифровывается для
    повторного использования.
  - Push: `events.watch()` регистрирует канал на наш webhook
    (`POST /calendar/google/webhook`), продлевается кроном ежедневно
    (`CalendarSyncCron`, `apps/api/src/calendar/calendar-sync.cron.ts`).
    Требует публичный HTTPS-урл (`GOOGLE_CALENDAR_WEBHOOK_URL`) — на
    localhost недостижим, поэтому в деве канал не создаётся.
  - Pull: инкрементально по `syncToken` (Google Calendar API), полный ресинк
    при `410 GONE`; подстраховка — фоновый pull каждые 15 минут на случай
    пропущенного webhook (раздел 22 ТЗ — не полагаться на единственный
    механизм доставки).
  - Push из нашей системы — best-effort: сбой синхронизации с Google не
    должен ронять создание/правку события внутри системы.
- **RBAC**: весь модуль (`GET/POST/PATCH/DELETE /events`,
  `/calendar/google/*`) — только `OWNER`, раздел 5 ТЗ (это личный календарь
  руководителя, не общий корпоративный). Исключение —
  `/calendar/google/callback` и `/calendar/google/webhook`: их дёргает сам
  Google (браузерный редирект и server-to-server push), без нашего Bearer-
  токена, поэтому они вынесены в отдельный `GoogleCalendarPublicController`
  без `JwtAuthGuard`. `callback` защищён коротко живущим (10 мин) подписанным
  `state`-токеном (JWT) вместо сырого `employeeId` в query — иначе это была
  бы открытая дыра для подмены подключения.
- **Что нужно от владельца, чтобы это заработало по-настоящему**: OAuth-
  клиент в Google Cloud Console (тип Web application) →
  `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_REDIRECT_URI` в
  `apps/api/.env` — без них подключение просто вернёт ошибку, остальная
  система на это не завязана (тот же паттерн, что и с `TELEGRAM_BOT_TOKEN`
  ниже).
- **Не реализовано**: входящий Telegram-бот, принимающий голос/текст
  напрямую в чате (голосовой ввод сейчас — через запись в браузере/WebView
  Mini App/Web App, `POST /voice/parse`, см. `CURRENT_STATE.md`), отправка
  писем (согласовано — всегда через подтверждение, без исключений),
  маршрутизация по направлениям бизнеса (владелец: пока не актуально для
  этой системы, но вероятно понадобится — обсуждали как лёгкий тег на
  `Employee`, не как возврат `Project`), MCP-клиент для Plaud в бэкенде
  (изучено — не даёт готового вебхука; вместо него работает OAuth +
  периодический CLI-поллинг через Plaud API, `apps/api/src/plaud/`).

## Текстовый и голосовой AI-чат «Ассистент» (Stage 2, Phases A–H, 20.09.2026)

Единственная вкладка «Ассистент» в `apps/miniapp` — с Phase H (20.09.2026)
объединяет текст и голос: микрофон встроен в composer (заменяет кнопку
отправки, когда поле ввода пустое), отдельной вкладки «Голос» в Mini App
больше нет. Персистентная переписка (`Conversation`/`Message`/
`MessagePart` в БД, не localStorage) — теперь и для голосовых реплик тоже:
`VoiceService`/`/voice/parse` сохранил свой собственный движок исполнения
(Whisper → Claude-каскад → мгновенная мутация задачи/события без
подтверждения — раздел "Календарь и голосовой AI-агент" выше), но пишет
результат в ту же ленту. Кросс-движковая память: модель в текстовом
сообщении видит и может сослаться на задачу, только что созданную голосом,
и наоборот. `apps/web` — отдельная десктоп-страница `/voice` (включая
диктовку со страницы встречи) не объединялась и не изменилась: там никогда
не было текстового AI-чата, объединять нечего, она продолжает работать
через тот же `/voice/parse` с прежними полями ответа.

Также в тексте: tool-calling поверх реальных `Task`/`Event` (модель не
сочиняет данные карточек), SSE-стриминг ответа с авторитетным
`userMessage` уже на `message.started`, вложения (загрузка/скачивание,
magic-byte + структурная OOXML-проверка DOCX/XLSX, компенсация storage/DB
при сбое, отдельная очистка незавершённых загрузок кроном, метаданные
текущего вложения видны модели в том же запросе), генерация файлов
(Phase G — выгрузка задач в `.xlsx` третьим tool-инструментом,
`export_tasks_xlsx`, тот же `FILE`-часть и то же скачивание, что и обычные
вложения), идемпотентность БД-строк под гонкой (`Message.replyToMessageId`
— `@unique`, конкурентные одинаковые запросы не создают дублей и не
падают — но это не то же самое, что exactly-once ВЫПОЛНЕНИЕ, см. ниже).
Подробности реализации, известные ограничения этого этапа (нет
frontend-тестовой инфраструктуры, узкий случай ненадёжного повторного
вызова `export_tasks_xlsx` при буквальном повторе запроса) и путь данных —
раздел "Assistant Chat" в `CURRENT_STATE.md`. Находки трёх внешних аудитов
20-21.09.2026 (exactly-once execution для текстового чата и для голоса под
конкурентными запросами, нетранзакционная линковка Message+FileArtifact,
`storage.delete()` глотавший не-ENOENT ошибки, `StorageRegistry`,
`FilesModule` DI) — закрыты, см. Phase F.3/H.1/H.2 в `CURRENT_STATE.md`.

## Привязка Telegram-аккаунтов

Раздел 14.2/14.3 ТЗ: подчинённые работают через Telegram Mini App. Руководитель
не знает Telegram-id сотрудника заранее, поэтому вместо ручного ввода id —
приглашение, а привязка происходит прямо в Mini App, без отдельного бота:

1. Руководитель на карточке сотрудника (`/employees/:id`) жмёт «Сгенерировать
   приглашение» → `POST /employees/:id/telegram-invite`. Токен одноразовый,
   действует 30 минут, хранится в БД только как хэш.
2. Руководитель передаёт ссылку (или токен) сотруднику лично, не публично.
3. Сотрудник переходит по `https://t.me/<бот>/<mini-app>?startapp=<token>` —
   открывается Telegram Mini App (Этап 2, фронтенд ещё не построен). Mini App
   получает `start_param = token` внутри подписанной Telegram `initData` и
   отправляет её на `POST /auth/telegram {initData}`.
4. Бэкенд проверяет подпись `initData` через HMAC с `TELEGRAM_BOT_TOKEN` (см.
   `apps/api/src/telegram/telegram-init-data.ts`, алгоритм — как в
   [документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app)).
   Подделать `initData` без знания токена бота невозможно — отдельный секрет
   между ботом и API не нужен. Если в `initData` есть `start_param` —
   привязывает Telegram к сотруднику из приглашения; если нет — это обычный
   вход уже привязанного сотрудника. В обоих случаях в ответ выдаётся тот же
   JWT, что и при обычном логине по паролю (`POST /auth/login`) — Mini App
   дальше работает как любой другой клиент.

Чтобы deep-link в приглашении был кликабельным, задайте `TELEGRAM_BOT_USERNAME`
и `TELEGRAM_MINIAPP_SHORT_NAME` (оба из @BotFather) — без них приглашение всё
равно работает, просто отдаётся сырой токен для ручной передачи. Отвязать
аккаунт: `DELETE /employees/:id/telegram-link`.

Mini App-фронтенд (`apps/miniapp`) — см. раздел ниже. Отдельный процесс бота
(long polling/webhook) для самой привязки не нужен — он потребуется позже
только для push-уведомлений (раздел 14.3 ТЗ).

## Telegram Mini App (раздел 14.2 ТЗ, 31.08.2026)

`apps/miniapp` — отдельное Next.js-приложение (не страницы внутри
`apps/web`): другой UX-язык (мобильный, свайп между режимами, полноэкранные
оверлеи вместо страниц), другая модель авторизации (Telegram `initData`, а
не форма логина), и по концепции «Адъютант» это в перспективе разные
траектории развития — Web App остаётся десктоп-инструментом руководителя,
Mini App растёт в сторону голосового AI-агента.

- **Авторизация** — `window.Telegram.WebApp.initData` (скрипт
  `telegram-web-app.js`, подключён в `layout.tsx` через `next/script`) →
  `POST /auth/telegram`, токен в `sessionStorage` (не `localStorage`, как в
  web) — Mini App переоткрывается заново при каждом запуске из Telegram, и
  Telegram сам документирует initData как токен на одну сессию, а не то,
  что стоит кэшировать надолго.
- **Дев-фолбэк без Telegram** — если `initData` пустая (открыто в обычном
  браузере — то есть всегда при локальной разработке без реального бота),
  показывается форма email/пароль через `POST /auth/login`. Это не
  «недоделанная авторизация», а осознанный фолбэк: без него нельзя было бы
  протестировать интерфейс без настоящего Telegram-бота.
- **Свайп-навигация** (`components/swipe-shell.tsx`) — pointer events,
  `touch-action: pan-y` на треке отдаёт вертикальный скролл контента
  браузеру нативно, JS перехватывает только горизонтальные жесты. Табы в
  шапке — альтернативный способ переключения (свайп плохо discoverable сам
  по себе). Хедер скрывается сам, если экран всего один (см. ниже про
  ролевую видимость).
- **Экраны**: «Задачи» (список по статусам → оверлей с карточкой, сменой
  статуса, комментариями — доступно всем), «Календарь» (агенда по дням,
  `OWNER`-only, та же RBAC-граница, что в Web App — подчинённому вкладка
  просто не показывается, а не показывается и падает в 403) и «Ассистент»
  (текст + голос в одном composer'е — запись → транскрибация → Claude tool
  use → выполненное действие прямо в общей ленте, см. раздел "Текстовый и
  голосовой AI-чат «Ассистент»" выше и `CURRENT_STATE.md`) — все три
  реализованы. Отдельной вкладки «Голос» с Phase H (20.09.2026) больше
  нет. Ручная постановка задачи через форму (не голосом/текстом) — тоже
  есть (`task-create-overlay.tsx`); импорт из Plaud внутри Mini App
  отдельным экраном не начат (сам импорт саммари уже автоматизирован на
  бэкенде, см. раздел "Встречи и источник задачи").
- **CORS**: `MINIAPP_URL` — отдельная переменная окружения (`apps/api/src/main.ts`),

## Встречи и источник задачи (раздел 8/9 ТЗ)

`Meeting` хранит транскрипт и саммари встречи из Plaud — изначально только
ручная загрузка (`/meetings/new`, раздел 20 MVP: "Загрузка Transcript +
Summary — ручная"), теперь дополненная автоматической синхронизацией:
`apps/api/src/plaud/` подключает Plaud через OAuth (`PlaudOAuthController`,
только `OWNER`) и периодически (крон `PlaudSyncCron`) импортирует новые
саммари (`auto_sum_note`) через Plaud API — транскрипт из Plaud сознательно
не переносится (см. план), курсор — `created_at` последней импортированной
записи. Оба пути пишут в одну и ту же модель `Meeting`, видно только
руководителю (`@Roles(OWNER)` на `MeetingsController`) — протокол может
касаться тем шире, чем задачи, которые из него извлечены (раздел 5 ТЗ).

- `rawTranscript`/`rawSummary` — исходные версии, неизменны (раздел 8.1 ТЗ).
  `enhancedTranscript`/`enhancedSummary` (замена `Speaker N` → имя,
  разбиение на темы) — поля уже есть в схеме, но всегда `null` до Этапа 4:
  это результат AI-обработки, которой ещё нет.
- Разбиение на `MeetingTopic` сознательно не заведено — это тоже продукт
  AI-сегментации (Этап 4); заводить пустую сущность под будущий функционал
  сейчас преждевременно.
- `Task.sourceMeetingId` + `sourceTimestamp` — ссылка на встречу и точный
  таймкод. `Task.sourceContext` — короткий curated-контекст происхождения
  задачи, **безопасный к показу исполнителю без доступа к самой встрече**:
  на карточке задачи видно название встречи, дату, таймкод и `sourceContext`
  всем, кто видит задачу, но сам протокол (`GET /meetings/:id`) — только
  руководителю. Ссылка на встречу на карточке задачи кликабельна только для
  `OWNER`; сотруднику она показывается как обычный текст.
- Аудио: поле `audioUrl` (путь во внешнем хранилище, не blob в БД) и
  `audioDeleteAt` (политика хранения, раздел 15 ТЗ) — в схеме заложены,
  загрузка файла ещё не реализована (нужно решить объектное хранилище).

## Деплой на продакшен (VPS)

Собственная инфраструктура на одном VPS через Docker Compose, а не разбросанные
по нескольким PaaS-провайдерам компоненты — это прямое следствие раздела 0 ТЗ:
весь смысл отказа от готового трекера был в контроле над данными, и это же
рассуждение применимо к выбору хостинга.

**Текущий продакшен**: `85.202.193.118`, домены `adyutant.glb-engineering.kz`
(Web App) и `api-adyutant.glb-engineering.kz` (API). Это общий VPS с другими
проектами компании — поэтому api/web публикуют порты только на `127.0.0.1`
(`3021`/`3022`), а наружу их обслуживает **уже существующий системный nginx**
(не в докере — на этой машине nginx уже держит 80/443 для других сайтов),
через дополнительные server-блоки (`infra/nginx/adyutant.conf.example` →
`/etc/nginx/sites-available/adyutant` на сервере) и certbot тем же способом,
что и для остальных доменов. Это отступление от общего случая ниже — на
чистом выделенном VPS проще поставить Caddy или nginx-в-докере, которые сами
берут 80/443 и TLS.

**Что нужно заранее (для нового VPS с нуля)**: Docker + Docker Compose plugin,
домен с двумя A/AAAA-записями на IP сервера. Так как npm workspaces —
монорепозиторий без отдельных публичных пакетов, доставка кода на сервер —
`rsync` (или `tar`+`scp`, если на машине разработки нет rsync — так было на
Windows-машине, где это разворачивалось), а не `git clone` (если не заведён
отдельный git-репозиторий с удалённым origin).

```bash
# с машины разработки — переносим код (без node_modules/.next/dist/.git/.env,
# см. .dockerignore/.gitignore)
rsync -az --exclude-from=.gitignore --exclude .git \
  ./ user@server:~/ai-task-system/

# на сервере
cd ai-task-system
cp infra/docker/.env.prod.example infra/docker/.env.prod
cp apps/api/.env.production.example apps/api/.env.production
# заполнить оба файла реальными значениями — пароль БД, домены, JWT_SECRET,
# ENCRYPTION_KEY (openssl rand -base64 32), Google/Telegram креды по мере
# готовности (без них соответствующие интеграции просто не заработают,
# остальная система на них не завязана — см. разделы выше).
# POSTGRES_PASSWORD генерировать БЕЗ URL-небезопасных символов (/ + = и
# т.п.) — DATABASE_URL склеивается из него напрямую в
# docker-compose.prod.yml, а не percent-encoded; проще всего
# `openssl rand -hex 24` вместо `-base64`.

cd infra/docker
# На маломощном VPS (~2GB RAM) собирать api и web параллельно (обычный
# `up -d --build`) рискованно — см. ниже про OOM. Собирать по одному:
docker compose -f docker-compose.prod.yml --env-file .env.prod build api
docker compose -f docker-compose.prod.yml --env-file .env.prod build web
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d

# сид (создание руководителя) — тот же ts-node, что и в разработке
# (npm run seed --workspace=apps/api), но напрямую: package.json не
# зарегистрирован в prisma.seed-конвенции, поэтому `prisma db seed` не
# сработает как единая команда.
docker compose -f docker-compose.prod.yml --env-file .env.prod exec -w /repo/apps/api api \
  node ../../node_modules/ts-node/dist/bin.js prisma/seed.ts
```

Дальше — свой server-блок в nginx на 127.0.0.1:3021/3022 (см.
`infra/nginx/adyutant.conf.example`) и `sudo certbot --nginx -d <домен>` на
каждый домен для TLS.

`prisma migrate deploy` (в отличие от `migrate dev`, который используется в
разработке) запускается автоматически при каждом старте контейнера `api` —
безопасно применяет только неприменённые миграции, без интерактивных
вопросов о потере данных. Сид (создание руководителя) — разовая ручная
команда, а не часть автозапуска, чтобы не создавать дубликат при каждом
рестарте контейнера.

Обновление после изменений в коде — `rsync` + пересборка (по одному сервису,
см. выше) + `up -d`: Docker пересоберёт только изменившиеся образы благодаря
кэшу слоёв.

**Известная проблема на маломощных VPS — OOM при сборке.** На сервере
`85.202.193.118` (Ubuntu 24.04, ~2GB RAM) `nest build` и `next build` падали
с `FATAL ERROR: ... JavaScript heap out of memory` на лимите ~1GB — это
собственный автоматически подобранный лимит хипа V8 исходя из физической
памяти хоста, а не нехватка памяти как таковая: добавление свопа не
помогало, потому что V8 никогда не пытался его использовать — упирался в
свой лимит раньше. Решение — явный `NODE_OPTIONS=--max-old-space-size=3072`
на build-стадии обоих Dockerfile (уже внесено в код, ничего дополнительно
делать не нужно), плюс сборка api/web по очереди, а не параллельно (см.
команды выше) — это снижает пиковую нагрузку, но именно OOM внутри одной
сборки решает только NODE_OPTIONS. На хосте также было мало свопа (2GB) —
добавили ещё 4GB (`fallocate`+`mkswap`+`swapon`) на всякий случай, это не
повредит даже если NODE_OPTIONS уже решает проблему сам.

**Файлы**: `apps/api/Dockerfile` и `apps/web/Dockerfile` (multi-stage,
собираются из корня монорепозитория — см. комментарии в файлах про
npm workspaces), `infra/docker/docker-compose.prod.yml`,
`infra/nginx/adyutant.conf.example`. `apps/web` собран с
`output: 'standalone'` (next.config.ts) — минимальный self-contained образ
вместо полного дерева монорепозитория; `apps/api` копирует node_modules
целиком (см. Dockerfile) — обрезка не стоит риска для монорепо на npm
workspaces при таком масштабе проекта.

Проверено полностью на реальном сервере 31.08.2026: сборка обоих образов,
все 8 миграций применены, сид руководителя, вход через
`https://adyutant.glb-engineering.kz` в браузере, логин через API — всё
отработало.
